How findings are dated, aged and scoped

The compliance export carries only the latest scan result, so ageing cannot be derived from it. This tool keeps its own record, keyed on host and rule, and updates that record each time an export is loaded.

Dating rules

  • A failure seen for the first time is recorded with the run's scan date as its first-found date.
  • A failure already on record keeps its original first-found date, however many times it reappears.
  • A rule that moves from fail to pass is closed and stamped with the run date.
  • A closed finding that fails again opens a new cycle with a new first-found date. The earlier cycle is kept in the history.
  • A host absent from an export is not treated as remediated. Its findings stay open and the host is reported as not scanned.

Warnings

Where the export reports results numerically, 0 is read as pass, 1 as warning and 2 as failed. Warnings are treated as open findings by default and aged the same way as failures, since a check that did not pass is not evidence of compliance. They are labelled separately everywhere so they can be reported apart from outright failures, and they can be excluded from a run instead — that choice is recorded in the run log and stated in the report.

Baseline findings

Failures present on the very first run have no observable start date. They are marked as baseline and dated from the day tracking began. Their true age is older than shown, and they are labelled as such wherever they appear.

Scope and coverage

The inventory defines the population. Inventory hosts that never appear in an export are reported as never scanned; hosts in an export that are absent from the inventory are reported as not inventoried. Neither is silently dropped.

Corrections

A run loaded in error can be reverted, which restores every finding to its state before that run. Findings can also be removed individually or by host. Every correction is written to the change log with its date, operator and stated reason.
